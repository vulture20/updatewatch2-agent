# Agent repository notes

Moved out of the parent `claude/CLAUDE.md` (2026-10-15, /doctor cleanup) so a session working only in this repo doesn't also load the server repo's commands/layout — and vice versa. The parent file still holds everything cross-cutting: project status/history, core architectural rules, key configurable behaviors, tech stack, license.

Agent (`agent/`) — a .NET Generic Host Worker Service (net10.0) solution:
- `src/UpdateWatch2.Agent/UpdateWatch2.Agent.csproj` — the service project:
  - `Configuration/` — `AgentOptions` (now including `RegistrationToken`/`ClientCertificateThumbprint`/`RegistrationRetryIntervalSeconds`/`CertificateRenewalLeadTimeDays`/`CertificateMaintenanceIntervalSeconds`), `IAgentConfigStore` with `Configuration/Windows/WindowsRegistryConfigStore` (`HKLM\SOFTWARE\UpdateWatch2\Agent`, ACL-restricted to Administrators/SYSTEM since it now holds a bearer secret) and `Configuration/Linux/LinuxFileConfigStore` (JSON at `/etc/updatewatch2/agent.conf`, owner-only file permissions for the same reason), selected at startup via `OperatingSystem.IsWindows()`/`IsLinux()`; `ILogLevelState`/`LogLevelState` (agent v1.0.13) — the mutable singleton `Program.cs`'s logging filters and `HeartbeatWorker`'s pushed-LogLevel handling both read/write, see the per-agent-settings-push bullet under "Key configurable behaviors to preserve".
  - `Certificates/` — `FileCaTrustStore` (the pinned server CA root(s) — a plain file, not the OS trust store; a COLLECTION since CA root rotation, `updatewatch2-server#6`, means this agent may trust more than one at once, `MergeAdditional` adding new roots purely additively, never removing one), `IClientCertificateStore` (`Load`/`Save`/`Delete` — thumbprint-scoped, `updatewatch2-agent#3`) with `Certificates/Windows/WindowsClientCertificateStore` (machine cert store, non-exportable) and `Certificates/Linux/LinuxClientCertificateStore` (`/etc/updatewatch2/agent.pfx`, owner-only; `Delete` is thumbprint-scoped there too, not a no-op — a self-heal-vs-renewal distinction found the hard way, see the self-heal note under Commands (agent)), `PinnedServerCertificateValidator` (chain + SAN check against ANY currently-pinned root, TOFU on first contact), `IAgentCertificateState`/`AgentCertificateState` (the gate `HeartbeatWorker`/`UpdateCheckWorker` wait on), `IRegistrationWakeSignal`/`RegistrationWakeSignal` (lets `HeartbeatWorker`'s self-heal wake `RegistrationWorker` immediately instead of waiting out its own poll interval — agent v0.14.2, see the self-heal note under Commands (agent)).
  - `Communication/` — `IServerClient`/`ServerClient` (fetch-CA, register, alive, report-updates, `DownloadFileAsync` for self-update payloads — `updatewatch2-agent#14`) — mutual TLS implemented; see the note under Commands (agent).
  - `UpdateCheck/` — `IUpdateChecker`; `WindowsUpdateChecker`/`Windows/WuaUpdateSession` (real WUApiLib COM integration, `updatewatch2-agent#7` — see the note under Commands (agent)); `LinuxUpdateChecker`/`Linux/{AptUpdateSession,DnfUpdateSession}` (real apt/dpkg and dnf/yum integration, `updatewatch2-agent#8` — see the note under Commands (agent)) selected via `Linux/LinuxPackageManagerDetector`; `NoOpUpdateChecker` (fallback for a Linux host with neither package manager, and previously the only Linux option before #8).
  - `SelfUpdate/` — `IAgentSelfUpdater`/`AgentSelfUpdateService` (self-update to a newer agent release the server offers, `updatewatch2-agent#14` — real test coverage: version/asset decision logic, download, SHA-256 verification), `IPlatformUpdateApplier` with `Windows/WindowsInstallerApplier` (re-runs the NSIS installer silently) and `Linux/LinuxPackageApplier` (`dpkg`/`rpm` inside a detached `systemd-run --scope`, not a plain child process — see the "Agent auto-update" bullet's standalone note on why that distinction matters), `NoOpAgentSelfUpdater` (fallback for a Linux host with neither package manager, mirroring `UpdateCheck/NoOpUpdateChecker`), `SelfUpdateStagingCleaner` (deletes downloaded update packages older than `AgentOptions.SelfUpdateStagingRetentionDays`, always keeping the most recent one) — see the "Agent auto-update" bullet under "Key configurable behaviors to preserve" for the full design and its live-verification caveats.
  - `RegistrationWorker.cs` — a persistent maintenance loop (not a run-once-at-startup task) driving the register-then-poll-until-approved-and-certified flow and, afterward, ongoing recovery if a certificate is ever lost mid-lifetime — see the note under Commands (agent).
  - `HeartbeatWorker.cs` / `UpdateCheckWorker.cs` — the two `BackgroundService`s driving the alive heartbeat and the jittered update-check loop; both wait on `IAgentCertificateState` before their loops start. Every heartbeat also re-sends this agent's current `DnsName`/`OperatingSystem`/`IpAddress`/`AgentVersion` (`updatewatch2-agent#6`, not to be confused with the identically-numbered but unrelated `updatewatch2-server#6` CA-rotation issue), not just at registration, since registration itself never runs again once an agent is certified. It also re-sends a fresh, lightweight "is a reboot required" check on every tick (agent v1.0.12/server v1.3.10, protocol `1.2.0`, at the user's explicit request — "Der Check, ob ein Neustart nötig ist, sollte öfter stattfinden. Wie hoch ist der Aufwand für diesen Check? Würde es den Server merklich belasten?") via `IUpdateChecker.CheckRebootRequiredAsync`, decoupled from the full, far slower update search (`CheckAsync`) so it can run far more often — confirmed cheap on every platform (a cached COM property read on Windows, a file-existence check on apt, a local subprocess spawn on dnf/yum — none touch the network), and the server-side cost of one more nullable field on the heartbeat is negligible. A failed check sends `null`, never a confirmed `false`, so a transient failure can't overwrite the server's last-known-good `Agent.RebootRequired` with a false negative — same discipline as `UpdateCheckResult.Success`. Not to be confused with `Reboot/IAgentRebooter` below, an unrelated feature (an admin *triggering* a reboot, not the agent *detecting* one is needed). `HeartbeatWorker` also polls `GET /api/version` each tick and logs a warning on a protocol-version mismatch (`updatewatch2-server#3`), checks/proactively renews its own client certificate before it expires (`updatewatch2-server#7`), fetches the server's published CA root bundle and pre-trusts any new one ahead of an eventual rotation activation (`updatewatch2-server#6`), acts on a remote-triggered install reported via `alive` (`updatewatch2-server#10`/`updatewatch2-agent#4`) — invoking `IUpdateChecker.InstallAsync` inline that same tick and acknowledging the outcome back to the server — and, on the same tick, a newer agent release the server offers (`updatewatch2-server#14`/`updatewatch2-agent#14`, handed off to `SelfUpdate/IAgentSelfUpdater` with no acknowledgement call needed), deletes old downloaded self-update packages via `SelfUpdate/SelfUpdateStagingCleaner`, and — last on the tick, since a successful reboot ends this very process shortly after — acts on a remote-triggered reboot via `Reboot/IAgentRebooter` (see "Remote reboot" under "Key configurable behaviors to preserve"). All piggybacked on the heartbeat cadence rather than a one-time startup check or a separate poll loop, so a server upgrade, an approaching expiry, a newly prepared CA root, a fresh install/release/reboot request, or old packages piling up mid-lifetime all get caught too, not just a condition present at the agent's own last startup — see the note under Commands (agent).
  - `Protocol/` — `ProtocolVersion` constant, `AgentApiRoutes` (route-template helpers matching the server's `api/agents/{hostname}/...` convention); `AgentVersion.cs` at the project root holds the agent version.
  - `Program.cs` — wires `AddWindowsService`/`AddSystemd` (safe no-ops off-platform), Windows Event Log logging, config-store/cert-store/update-checker platform selection, the shared `SocketsHttpHandler` (client cert + pinned-CA validation) and a separate bootstrap-`IServerClient` factory `RegistrationWorker` uses (see the note under Commands (agent) on why these must not share a connection pool).
  - `icon.ico` — the compiled binary's `<ApplicationIcon>` (csproj); Windows-only, no-op on Linux builds.
- `tests/UpdateWatch2.Agent.Tests/` — xUnit; `LinuxFileConfigStoreTests`/`LinuxClientCertificateStoreTests` (Linux-only, see their `[SupportedOSPlatform]` attribute), `PinnedServerCertificateValidatorTests`, `AgentCertificateStateTests`, `RegistrationWorkerTests`, `WorkerTests` (now also asserting Heartbeat/UpdateCheck make zero calls before the certificate state is ready) — all hand-written fakes, no mocking library.
- `installer/nsis/setup.nsi` — NSIS installer: installs/upgrades the `UpdateWatch2 Agent` Windows service from a self-contained win-x64 publish output, prompts for (or accepts silently via `/SERVERADDRESS=`/`/SERVERPORT=`) the server address/port and writes them to `HKLM\SOFTWARE\UpdateWatch2\Agent`, and, additively, `/CACERT=<path>` (silent-only, agent v0.15.0) to pre-seed the agent's CA trust store before its first service start — see the trust-on-first-use note under "Certificate-based mutual auth" below. Built by `.github/workflows/release.yml` on a tag push; see that workflow and the repo README's "Installation" section.

## Commands (agent)

Same .NET 10 SDK, run from `agent/`:

```
dotnet build       # build the whole solution
dotnet test        # run all tests
dotnet run --project src/UpdateWatch2.Agent   # run the service in the foreground (not installed as a service)
```

The agent targets both Windows and Linux from one codebase — platform-specific code (registry vs. config file, `WindowsUpdateChecker` vs. `LinuxUpdateChecker`/`NoOpUpdateChecker`, the two `IClientCertificateStore` implementations) is selected at startup via `OperatingSystem.IsWindows()`/`IsLinux()` checks in `Program.cs`, not via separate build configurations. When adding another Windows- or Linux-only class, mark it `[SupportedOSPlatform("windows")]`/`[SupportedOSPlatform("linux")]` and make sure its registration site is guarded by an explicit `if (OperatingSystem.IsWindows())` / `else if (OperatingSystem.IsLinux())` — not a ternary, and not just the implicit `else` of the other platform's check (a bare `else` on the Linux branch was flagged by `CA1416` when `WindowsClientCertificateStore`/`LinuxClientCertificateStore` were added — fixed by making it an explicit `else if`). `CA1416` catches this at build time as a warning, not an error — don't rely on the build failing, check the warning list; it doesn't recognize ternaries or implicit `else` as guards, only explicit `if`/`else if` naming the platform.

**Bug: registration's bootstrap HTTP calls (fetching the CA certificate, every registration poll) must run over their own, separate `HttpClient`/handler — never the shared one `IServerClient` uses for everything else.** [Found only by a real end-to-end run, not any unit test]: registration succeeded (certificate received/installed), but every subsequent `alive`/`updates` call got 403 as if no certificate had been presented. Root cause: .NET's `SocketsHttpHandler` pools keep-alive connections per (scheme, host, port) and reuses them regardless of whether a client certificate is added to `SslOptions` afterward — `SslOptions` is only consulted when a *new* TLS connection is negotiated. Connections `RegistrationWorker` opened *before* a certificate existed stayed pooled and got reused for the first "real" calls too. Fix: bootstrap traffic gets its own throwaway `HttpClient`/handler/connection pool (via a `Func<IServerClient>` factory registered in `Program.cs`, so tests can substitute a fake) — the shared handler used by `HeartbeatWorker`/`UpdateCheckWorker` is now touched only to attach the certificate to its `SslOptions.ClientCertificates`, never to make a call itself before that point. Re-verify with a live run (not just `dotnet test`) if you touch this wiring — `WorkerTests`/`RegistrationWorkerTests` use hand-written fakes and can't catch a real connection-pooling interaction like this.

**The shared `AddHttpClient<IServerClient, ServerClient>` also wraps the handler in `Microsoft.Extensions.Http`'s own automatic per-request logging — found while extending the log-level audit (see Commands (server)), not a live incident.** Every `alive`/`report-updates`/`install-ack`/`reboot-ack`/`renew`/CA-bundle-fetch call already produced a second, independent set of "Start/End processing HTTP request", "Sending"/"Received" and (on failure) "HTTP request failed" lines, hardcoded at Information, on top of `ServerClient`'s own explicit `LogDebug` lines for the same request, visible at the default log level with no Debug needed. Only the separate bootstrap client (built via `new HttpClient(bootstrapHandler)`, never through `AddHttpClient`) is unaffected. Fixed (agent v1.0.22) by demoting all five messages (the fifth, "HTTP request failed after {ElapsedMilliseconds}ms", EventId 104, found only while implementing this) to Debug-only: `Program.cs` registers two more category-specific `builder.Logging.AddFilter(...)` calls targeting `System.Net.Http.HttpClient.IServerClient.{LogicalHandler,ClientHandler}`, reading the same mutable `logLevelState.Current` — reuses the exact delegate mechanism `ILogLevelState` already provides for a server-pushed LogLevel change, taking effect the moment `HeartbeatWorker.ApplyPushedSettings` calls `logLevelState.Update(...)`. [Live-verified against a throwaway harness with a real `AddHttpClient` client pointed at a deliberately unreachable host: at "Information" none of the seven category lines appear, including on a genuine connection-refused error with a full stack trace; at "Debug" all appear as before].

**`RegistrationWorker` is a persistent maintenance loop for the process's lifetime, not a run-once-at-startup task** (`updatewatch2-server#8`/`updatewatch2-agent#3`) — a deliberate redesign: the original one-shot version returned for good once a certificate was attached, so a certificate lost later in the process's life had nothing left running to notice it, and only a service restart could recover. Every iteration now re-checks `IClientCertificateStore.Load()`; if null, the loop re-reads `IAgentConfigStore.Load()` directly (bypassing the cached `AgentOptions` DI singleton), so a fresh registration token an admin writes into the registry/config file — via the admin UI's "Reissue certificate" action, `AgentService.ReissueCertificateAsync` server-side — is picked up on the next poll with **no agent service restart required**. [Live-verified specifically for that claim: a real agent left running, its on-disk certificate deleted out from under it, a fresh token obtained via the admin API and written into its config file in place, and the same OS process (same PID, same start time) recovered on its own within one maintenance-interval tick]. Two non-obvious things surfaced: (1) deleting the on-disk certificate does **not** retroactively affect the already-loaded `X509Certificate2` object the shared `SocketsHttpHandler.SslOptions.ClientCertificates` holds — heartbeats keep succeeding on the old in-memory certificate until the *server* invalidates it (e.g. the moment an admin actually clicks Reissue, not when the local file happens to go missing); (2) in the handoff window between a reissue clearing the server-side certificate fields and the agent's next poll picking up the new token, a request still carrying the old empty/stale token gets a transient 409 Conflict — expected, self-resolving on the very next retry tick, not a bug to chase.

**Proactive certificate renewal lives on `HeartbeatWorker`, not `RegistrationWorker`, and reuses the already-certified shared handler** (`updatewatch2-server#7`) — piggybacked on the alive-heartbeat cadence via `AgentOptions.CertificateRenewalLeadTimeDays` (default 60 days before `NotAfter`, read straight off the locally-stored certificate — no server round-trip needed) and a new `POST .../renew` call authenticated by the CURRENT still-valid client certificate, not a registration token. On success the worker hot-swaps `SslOptions.ClientCertificates` (`Clear()` then `Add()` — never just `Add()` alongside the old one, which would leave two certificates simultaneously eligible for TLS client-cert selection) and calls `IClientCertificateStore.Delete` on the previous thumbprint *after* `Save`, not before — if `Delete` were to fail, this order leaves the agent with a working new certificate plus an orphaned old store entry, never with no working certificate at all. [Live-verified end to end: old certificate confirmed rejected (403) immediately after the swap, new certificate confirmed accepted, `agent.certificate.renew` audit entry confirmed on the server].

**`HeartbeatWorker` self-heals after the server stops trusting a certificate the agent still has loaded** (`updatewatch2-server#11`/`updatewatch2-agent#5`) — the gap renewal/re-issuance deliberately left open: an admin reissuing a certificate for an agent still running fine (suspected compromise, not loss) gets no automatic recovery from either of those features, since both only react to the certificate being genuinely *absent* locally. `SendAliveAsync` now returns an `AliveOutcome` (`Success`/`CertificateRejected`/`OtherFailure`) instead of swallowing the status code; two **consecutive** `CertificateRejected` results (a real 401/403 round-trip, never a network exception — the counter resets on anything else) make `HeartbeatWorker` call `IClientCertificateStore.Delete` on the now-untrusted certificate and clear `SslOptions.ClientCertificates`, so `RegistrationWorker`'s existing lost-certificate recovery path picks it up unmodified. [A live run — server reissues while the agent keeps running, nothing touched locally — caught two real bugs no unit test could have]: (1) `LinuxClientCertificateStore.Delete` had been written as an unconditional no-op — correct for the *renewal* call pattern, silently wrong for self-heal (no preceding `Save`, so `Load()` kept finding the rejected certificate forever) — fixed by making it thumbprint-scoped like the Windows store already was. (2) Even after that fix, a freshly recovered certificate got immediately re-rejected and stranded the agent (the one-shot registration token was already consumed) — caused by the 2-minute `PooledConnectionLifetime` set for the renewal work above: self-heal-then-recover changes `SslOptions.ClientCertificates` twice within a far shorter window than any nonzero pooled-connection lifetime, so a stale pooled connection kept getting reused and presenting nothing even after the new certificate was attached. Fixed by setting `PooledConnectionLifetime = TimeSpan.Zero` — disabling pooling entirely, which this agent's low request volume makes free. Re-verify live (not just `dotnet test`) if you touch either the pooling setting or either `IClientCertificateStore.Delete` implementation — both bugs were invisible to hand-written-fake unit tests. **A third gap, found by a user report: recovery sometimes appeared to simply never happen.** It did, just slowly — `RegistrationWorker`'s "certificate present" branch only re-checks `IClientCertificateStore.Load()` once every `AgentOptions.CertificateMaintenanceIntervalSeconds` (15 min default), on a completely independent timer from `HeartbeatWorker`'s own self-heal, with nothing logged in between — worst case, up to two heartbeat intervals plus the full maintenance interval, ~25 minutes of total silence. Fixed with `Certificates/IRegistrationWakeSignal` (agent v0.14.2): self-heal now calls `RequestImmediateCheck()` the moment it drops a rejected certificate, waking `RegistrationWorker`'s sleep immediately — `CertificateMaintenanceIntervalSeconds` is now only the *upper bound*. Also closes a related gap: if a certificate goes missing through a path this agent's own code didn't drive, `certificateStore.Load()` was already null by the time self-heal ran, and its old "already gone, nothing to do" early return skipped clearing `SslOptions.ClientCertificates` — that branch now clears the handler and wakes registration too.

**A fourth gap, raised by a user question about the README: a forced re-issuance token could sit unused indefinitely unless an admin also remembered to clear `ClientCertificateThumbprint` by hand.** Confirmed a real, code-level gap: `RegistrationWorker`'s certificate-present branch never looked at `RegistrationToken` at all, so a fresh admin-issued token placed while the agent was still running fine just sat there unused; recovery only happened once the server rejected the old certificate enough times for self-heal to notice. Fixed (agent v0.14.3): `RegistrationWorker` now re-reads the config store even while a local certificate is present, and if the token differs from the one already consumed, proactively drops the old certificate (`Delete` + clearing `SslOptions.ClientCertificates`) before registering with the new token on that same loop iteration — the identical drop-and-recover move self-heal already performs, just triggered by the token's presence instead of a rejection. An admin now only ever needs to place the fresh `RegistrationToken`; README/README.de spell out both the automatic behavior and, for older builds, the manual workaround this replaces.

**A network timeout during registration used to silently and permanently end `RegistrationWorker` — found via a real incident (a deleted agent, hostname `hpn54l`, that never re-registered), not by inspection.** The loop's safeguard was `catch (Exception ex) when (ex is not OperationCanceledException)`, assuming `OperationCanceledException` only ever means the worker's own `stoppingToken` was cancelled — a real shutdown. False: `HttpClient`'s own request timeout (100s default) surfaces as `TaskCanceledException`, an `OperationCanceledException` subtype unrelated to `stoppingToken`. Such an exception fell through into the loop's outer `catch (OperationCanceledException) { }` (meant only for a genuine shutdown), swallowed with **zero log output**, ending the loop for the rest of the process's life — no crash, no restart, nothing in `journalctl`. Fixed by checking `stoppingToken.IsCancellationRequested` explicitly: only an actual shutdown-triggered cancellation is let through; every other exception is now logged and the loop retries. The identical bug pattern existed unchanged in every try/catch across `HeartbeatWorker`/`UpdateCheckWorker` too (agent v0.12.1) — fixed identically there. [Confirmed by a throwaway harness reproducing the exact exception shape, plus the full `dotnet test` suite; not yet re-confirmed against `hpn54l` itself]. **A related but distinct gap, reported directly by the user (agent v1.0.9): some Alive/ReportUpdates calls hit a ~15s transport-level timeout in the field, each occurrence costing a whole worker interval rather than a quick retry — flagged as a plausible contributor to `updatewatch2-agent#20`'s TLS-abort reports.** Fixed with `ServerClient.WithRetryAsync` wrapping every outbound call (`SendAliveAsync`, `ReportUpdatesAsync`, `RegisterAsync`, `AcknowledgeInstallAsync`/`AcknowledgeRebootAsync`, `FetchVersionAsync`, `RenewCertificateAsync`, `FetchCaCertificateAsync`/`FetchCaCertificateBundleAsync`, `DownloadFileAsync`): up to 3 attempts total, 2s delay between, retried only on a response-less `HttpRequestException` (`StatusCode: null`), `IOException`, `SocketException`, or `TaskCanceledException` — never on a real HTTP error response (doesn't touch the transient-409 handoff case above or a genuine 401/403). `DownloadFileAsync` wraps the entire request-and-copy; `File.Create` truncates on every attempt. Real unit tests confirm a within-3-attempts success, a persistent failure giving up after exactly 3, and that a real HTTP error is never retried. **Confirmed by the user in practice, this fix apparently resolved `updatewatch2-agent#20`/`updatewatch2-server#22` — both closed** ("wurden beide mit dem Retry-Mechanismus scheinbar behoben. Der Fehler tritt so nicht mehr auf.") — the underlying WSAECONNABORTED root cause (issue #20's own leading hypothesis was Windows Defender Network Protection) was never actually diagnosed, only theorized; treat this as "the practical symptom stopped happening," not "the root cause is understood."

**Separately found while diagnosing the same incident: the agent's `LogLevel` setting was never actually applied.** `Program.cs` read a configuration key (`UpdateWatch2:LogLevel`) nothing in this codebase ever sets, instead of `AgentOptions.LogLevel`, always silently falling back to `"INFO"`. Fixed to read `AgentOptions.LogLevel`, also writing the resolved level directly into `builder.Configuration["Logging:LogLevel:Default"]` before `builder.Build()` (same `SetMinimumLevel`-doesn't-work asymmetry the server side already documents). [Confirmed by hand with a throwaway console harness]. **A further gap, found by a later user report: even with that fix, DEBUG messages still never reached Event Viewer** ("auch auf DEBUG liefert er keinerlei Einträge für die neuen COM-Logmeldungen"). Root cause: `AddWindowsService()` auto-registers a hardcoded `Warning`-level floor filter scoped specifically to `EventLogLoggerProvider` whenever running as a real Windows Service, more specific than — and silently overriding — the generic `Logging:LogLevel:Default` write regardless of order. Fixed (agent v1.0.8) two ways, deliberately redundant at the time since this couldn't be tested live: a `Logging:EventLog:LogLevel:Default` write plus a code-level `builder.Logging.AddFilter<EventLogLoggerProvider>(...)` call after `AddWindowsService()`'s own. **Since confirmed against a real Event Viewer**: DEBUG-level entries do reach it once both fixes are in place. **A follow-up finding, reported directly (agent v1.0.11): log entries were split across two Event Log sources** — SCM start/stop messages ("Service stopped successfully."/"Service started successfully.") under `"UpdateWatch2 Agent"` (space), everything else under `"UpdateWatch2.Agent"` (dot). Two unrelated causes: (1) a dead, duplicate `builder.Logging.AddEventLog(...)` call, alongside `AddWindowsService()`'s own auto-registered `EventLogLoggerProvider` (source defaulting to `IHostEnvironment.ApplicationName`, i.e. the entry assembly name, `"UpdateWatch2.Agent"`, dot) — both calls register a provider under the exact same `TryAddEnumerable` key, so the explicit call was silently dropped as a duplicate and had never actually taken effect — removed; (2) `WindowsServiceLifetime : ServiceBase`'s `AutoLog` (default true) independently defaults its own `EventLog.Source` to `ServiceBase.ServiceName` (space form — must stay unchanged, matches the SCM-registered service name `setup.nsi` creates). Fixed by redirecting: `serviceBase.EventLog.Source = "UpdateWatch2.Agent"` set explicitly before `host.Run()`; the two remaining raw `EventLog.WriteEntry("UpdateWatch2 Agent", ...)` crash-path calls switched to the dot source too. **Since confirmed against a real Event Viewer**: entries now land consistently under the `UpdateWatch2.Agent` (dot) source, with SCM start/stop messages the sole intentional exception under the space form.

**A separate, later incident on `hpn54l` (agent v0.12.1) produced the identical symptom — registration silently never happening, zero log output — from a completely different cause: `installer/linux/updatewatch2-agent.service` never set `WorkingDirectory=`.** Without it, systemd defaults cwd to `/`; the .NET Generic Host derives `ContentRootPath` from cwd, and its config-reload file watcher then recurses the *entire* tree under that root — on this host, an NFS-mounted backup share (`172.16.12.3` is the server; the share itself was a different host, `172.16.17.2:/mnt/data`) alone accounted for 170,000+ registered `inotify` watches and still climbing [caught live via `strace`]. Nothing got to run a single iteration, since this walk happens synchronously during host construction — indistinguishable from the agent being hung. Fixed by adding `WorkingDirectory=/opt/updatewatch2-agent` to the unit (both on that host and the repo's installer template) — [confirmed live: after `daemon-reload` + restart, `Content root path: /opt/updatewatch2-agent` appeared in the first log line, and a fresh, unapproved `hpn54l` row appeared moments later]. A packaging gap, not one-off — worth checking `WorkingDirectory`/cwd and `strace -p <pid>` for stuck directory-walk syscalls if a future report looks like this again. (agent v0.12.2) **A third fresh-install packaging gap, reported directly: the Linux agent crashed outright on a host with no ICU library installed** ("Couldn't find a valid ICU package installed on the system", `Environment.FailFast` out of `System.Globalization.CultureInfo`'s static initializer) — the correct package name varies by distro/release (`libicu76`/`libicu72`/`libicu70`/`libicu67`/`icu-libs`/...), so no single `.deb`/`.rpm` `Depends:` could be correct everywhere. Fixed (agent v1.0.6) by enabling `<InvariantGlobalization>true</InvariantGlobalization>` — removes the ICU dependency entirely, confirmed safe (grepped for every non-Ordinal/non-Invariant string comparison or culture-sensitive `ToUpper`/`ToLower`/`ToString` call — none exist). [Confirmed the resulting `runtimeconfig.json` actually carries `"System.Globalization.Invariant": true`, and ran the binary for real, confirming a clean start with no error output; the specific "ICU genuinely absent" crash itself wasn't re-reproduced, since the dev sandbox already has ICU installed].

**A real Windows production crash — reported via an APPCRASH entry (agent v0.14.2), the agent having gone unresponsive shortly before — turned out to be Generic Host's own shutdown path crashing the process, not application code.** The stack trace was an unhandled `OperationCanceledException` from `WindowsServiceLifetime.StopAsync`, propagating uncaught through `Host.StopAsync` → `WaitForShutdownAsync` → `RunAsync` → `Run` → `Main` — Generic Host throws this when stopping all `IHostedService`s takes longer than `HostOptions.ShutdownTimeout` (a 5-second default never overridden), and nothing in `Microsoft.Extensions.Hosting` catches it for you; `Program.cs`'s bare `host.Run()` had no try/catch at all, crashing the whole process instead of just failing to stop cleanly. A strong candidate for why 5s wasn't enough: `WindowsUpdateChecker`'s `Task.Run(...)` only lets its token cancel the work item before it starts — `WuaUpdateSession`'s synchronous COM calls, once in flight, can't be aborted mid-call, so a stop during a real Windows Update search/download/install can legitimately take far longer than any short timeout allows — an honestly-flagged live-verification gap `updatewatch2-agent#7` already carried, now with a production crash as a plausible real consequence. Fixed two ways (agent v0.15.1): `HostOptions.ShutdownTimeout` raised to 30 seconds (a mitigation, not a full fix — a real in-progress WUA install still can't be bounded by any timeout this codebase controls), and `host.Run()` wrapped in a try/catch for `OperationCanceledException` that logs a Warning directly to the Windows Event Log (`System.Diagnostics.EventLog.WriteEntry`, same `SourceName` the app's own `EventLogLoggerProvider` already uses) rather than through the app's normal DI-backed logging — `host.Services` is already disposed by the time this exception reaches `Main`, since `RunAsync`'s own `finally` disposes the host before the exception propagates out of it — and exits instead of crashing. Not unit-testable on Linux CI — re-confirm on a real Windows host the next time this is easy to trigger on purpose (stop the service mid-install).
